예제 프롬프트
  1. 윤도현 온보딩 해줘. 계정 dohyun, email·vpn 권한, 환영 메일까지
    • 작업 번호(J001)가 나오고 채팅이 바로 풀린다
    • 모델은 b.parallel_unsafe처럼 계정생성·email·vpn·메일을 한 턴에 몰아서 계획한다 — 그런데도 오른쪽 패널에는 create_account 딱 하나짜리 카드만 뜬다. 우리가 이 배치를 직접 갈라서 하나씩 보여주기 때문
  2. 박민수한테 prod-db 권한 줘
    • 작업 번호(J002)가 하나 더 배정된다
    • 이제 패널에 승인 대기 카드가 동시에 2개 떠 있다 — thread_id 가 달라 완전히 분리된 대화라서
  3. 윤도현 계정 상태 알려줘
    • 두 작업이 대기 중인 동안에도 대화는 안 막힌다
    • 2단계였다면 이 메시지조차 못 보냈다
  4. 진행 상황 알려줘
    • 메인 에이전트가 list_jobs 로 "J001 대기중 · J002 대기중" 을 답한다
  5. 이제 패널에서 하나씩 처리해 보자
    • J002(박민수 prod-db) 거부 — 즉시 종료, 워커가 거부 사실을 보고하고 마무리
    • J001(create_account) 승인 — 끝이 아니다. grant_access(email) 카드가 바로 이어서 뜬다 — 모델을 다시 부르지 않고도 그렇다(이미 한 턴에 계획해 뒀으니까)
    • J001 을 email → vpn → 환영 메일까지 계속 승인 — 매번 카드엔 도구 하나뿐이지만, a.sequential처럼 승인할 때마다 모델을 다시 호출하는 왕복은 없다

"병렬로 계획하되, 승인은 절대 안 몰린다"가 이 변형의 핵심이다 — a.sequential/(강제로 하나씩 계획, 매번 모델 재호출)과 b.parallel_unsafe/(계획도 병렬, 승인도 통째로 — 그래서 위험)와 비교해 볼 것.
