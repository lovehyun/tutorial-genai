# 3단계 — 서브에이전트 위임, 그리고 승인 요청을 어떻게 자르느냐

2단계의 한계("승인 카드가 뜨면 대화가 멈춘다")를 서브에이전트로 풀면, 새로운 질문이 하나 생긴다 —
**모델이 한 턴에 여러 도구를 한꺼번에 계획하면, 그 승인 요청을 어떻게 사람에게 보여줄 것인가?**
이 질문 하나에 답이 세 가지라 폴더를 셋으로 나눴다.

| 변형 | 포트 | 방식 | 트레이드오프 |
|---|---|---|---|
| [`a.sequential/`](a.sequential/) | 5083 | 모델이 한 턴에 도구 하나만 계획하도록 강제 (`parallel_tool_calls=False`) | 안전 — 승인 카드는 항상 도구 하나. 대신 승인마다 모델을 다시 불러야 해서 느리고, 온보딩 하나에 승인이 여러 번 필요해 피로가 쌓인다 |
| [`b.parallel_unsafe/`](b.parallel_unsafe/) | 5086 | 모델이 병렬로 계획하면 그 배치를 그대로 한 카드에 몰아서 보여준다 | 빠름 — 대신 사람이 4개를 한 번에 승인/거부해야 해서, 위험한 것 하나가 안전한 것들 사이에 섞여도 못 알아챌 수 있다 |
| [`c.parallel_guarded/`](c.parallel_guarded/) | 5087 | 모델은 병렬로 계획하게 두되, 그 배치를 우리가 직접 갈라서 하나씩 승인받는다 | 절충 — 모델 왕복은 `b`처럼 한 번, 승인 카드는 `a`처럼 하나씩 |

세 폴더 모두 2→3단계의 기본 변경(메인/워커 에이전트 분리, 백그라운드 위임, `asyncio.Event`로
재우고 깨우기)은 동일하다 — 그 부분은 [`b.parallel_unsafe/CHANGES.md`](b.parallel_unsafe/CHANGES.md)에
정리돼 있고, `a`/`c`의 `CHANGES.md`는 `b` 대비 달라진 부분만 적어 뒀다.

## 왜 이 질문이 중요한가

`b`가 우연이 아니라 **기본 동작**이라는 걸 실제로 확인했다 — gpt-4o-mini 에게
"계정 만들고 email·vpn 권한 주고 환영 메일까지 보내줘"를 시키면, 모델은 이걸 네 번에
나눠 순서대로 묻는 대신 **한 턴에 네 개를 한꺼번에 계획**해서 요청하는 경우가 있다.
`interrupt_before=["tools"]`는 "AI 턴 하나"마다 멈추는 것이지 "도구 호출 하나"마다 멈추는
게 아니므로, 그 네 개가 승인 카드 한 장에 통째로 실린다. 승인 게이트의 원래 취지
("위험한 것마다 사람이 본다")가 여기서 조용히 무너질 수 있다.

이건 4단계(`a.tool_name_only`)의 "자동승인이 도구 이름 단위라 인자를 못 본다"는 문제와
같은 뿌리다 — **굵은 단위의 자동화는 위험도를 못 본다**는 교훈이 승인 요청 단위(3단계)와
자동승인 등록 단위(4단계 `a`), 두 층에서 반복된다.

## 실습 순서

`a` → `b` → `c` 순서로 켜서 **같은 형태의 프롬프트**(각 폴더의 예제 프롬프트 참고 —
온보딩 대상만 3a=정다은/3b=한소연/3c=윤도현으로 다르다)를 시도해 보면, 승인 카드가
뜨는 모양이 셋 다 다르다는 걸 직접 비교할 수 있다.

> 온보딩 대상을 변형마다 다르게 둔 이유: 셋 다 같은 `ops.db`를 공유하는데(위 표의 포트가
> 다를 뿐 DB는 하나다), 같은 사람으로 셋을 순서대로 실습하면 두 번째·세 번째 변형은 이미
> 온보딩이 끝난 상태를 보게 된다 — 카드 개수·모양 비교라는 목적 자체는 여전히 되지만,
> 모델이 "이미 다 되어 있다"고 판단해 도구 호출을 아예 안 할 수도 있어 데모가 안정적이지
> 않다. 그래서 변형마다 계정 없는 신입을 따로 배정했다.
