예제 프롬프트
  1. 한소연 온보딩 해줘. 계정 soyeon, email·vpn 권한, 환영 메일까지
    • 작업 번호(J001)가 나오고 채팅이 바로 풀린다
    • 오른쪽 패널에 J001 이 "승인 대기"로 뜬다 — 카드 안을 자세히 볼 것: create_account·grant_access(email)·grant_access(vpn)· send_email 이 한 카드에 전부 몰려 있다. 모델이 이 온보딩을 네 단계로 나눠 하나씩 묻는 대신, 한 턴에 계획을 다 세워 한꺼번에 요청한 것 — 승인/거부 버튼은 딱 하나뿐이라 넷을 따로 판단할 수 없다
  2. 박민수한테 prod-db 권한 줘
    • 작업 번호(J002)가 하나 더 배정된다
    • 이제 패널에 승인 대기 카드가 동시에 2개 떠 있다 — thread_id 가 달라 완전히 분리된 대화라서
  3. 한소연 계정 상태 알려줘
    • 두 작업이 대기 중인 동안에도 대화는 안 막힌다
    • 2단계였다면 이 메시지조차 못 보냈다
  4. 진행 상황 알려줘
    • 메인 에이전트가 list_jobs 로 "J001 대기중 · J002 대기중" 을 답한다
  5. 이제 패널에서 처리해 보자
    • J002(박민수 prod-db) 거부 — 즉시 종료, 워커가 거부 사실을 보고하고 마무리
    • J001 승인 — 버튼 하나로 계정 생성·email·vpn·메일 발송이 한 번에 전부 실행된다. 넷 중 하나만 이상해도(예: 엉뚱한 그룹이 섞여 있어도) 카드를 대충 읽었다면 몰랐을 것이다

"한 카드에 네 개"가 이 변형의 핵심 문제다 — a.sequential/(하나씩 승인, 대신 피로 누적)과 c.parallel_guarded/(병렬은 유지하되 위험한 것만 따로 승인)와 비교해 볼 것.
